# DECISIONS.md — assumptions & technical decisions

Spec §9: "if a feature's behaviour is ambiguous, record your assumption **before** implementing it".
Format: `D-xx | decision | why | status`. Add new entries; never silently change old ones.

## Assumptions about behaviour

| ID | Assumption | Why |
|---|---|---|
| A-01 | Approving payment immediately triggers provisioning in the same request (synchronous); admin sees the result. | Simplest observable flow for AC-03/04; background queue is unnecessary at this scale. |
| A-02 | Retry is admin-only, only from `Failed`, max 5 attempts per order. The customer sees «خطا در فعال‌سازی – در حال پیگیری». | "Controlled retry" (§4.3); avoids customers hammering the external API. |
| A-03 | Cancel is allowed only in `PendingPayment` (by the owner or an admin). | Paid orders need a refund flow, which is out of scope (§5). |
| A-04 | A customer may have several orders; each order maps to at most one Drive service. | Idempotency unit = order (§4.3 "per order/subscription"). |
| A-05 | Price and quota are snapshotted on the order at creation time. | Later price edits by admin must not change existing orders. |
| A-06 | External user id = `abrit-ord{Jalali year}-{sequence}` derived from the order number (`ABR-1405-000124` → `abrit-ord1405-000124`), identical in Mock and Real mode; Team group = `{external id}-team`. Fallback for orders without a number: `abrit-{OrderId}`. | Deterministic and unique per order (order numbers are unique and immutable), readable for support. The year is kept because the sequence restarts every Jalali year (A-13) - a bare `abrit-ord000124` would collide next year. Replaces the earlier `abrit-{OrderId}` rule. |
| A-07 | No Nextcloud password is generated for display. The account is created with the customer's email; Nextcloud sends the set-password email. | §7: never show Nextcloud password in UI or logs. |
| A-08 | Team plan (required scope): display + order + provisioning of an owner account and a group. Member management = bonus (phase 09). | §3 table: real multi-user is a bonus. |
| A-09 | "Callback" in AC-05 is simulated by an HMAC-signed `POST /api/payments/mock-callback`. | There is no real gateway (§5) but AC-05 needs a repeatable callback. |
| A-10 | Accessing another customer's order returns 404, not 403. | Doesn't reveal that the order exists. |
| A-11 | UI is Persian only; dates in Jalali calendar. | §4.2 Persian RTL UI. |
| A-12 | Email confirmation on registration is off in the demo; password reset email goes to smtp4dev. | Keeps AC-01 testable locally. |
| A-13 | Order number = `ABR-{Jalali year}-{6-digit sequence}` (e.g. `ABR-1405-000124`); the Jalali year comes from `UtcNow` via `PersianCalendar` and the sequence restarts at 1 each Jalali year. Allocation is serialized by a per-year lock and committed immediately, so numbers are unique but may have gaps if an order save fails afterwards. | Human-readable and sortable; gaps are harmless, duplicates are not. Using UTC means the year can roll over up to 3.5h off Tehran's Nowruz midnight - acceptable for a demo. |
| A-14 | Ordering an unknown plan id and ordering a plan with `IsOrderable=false` both fail with the same `PlanNotOrderableException`. | Input validation without revealing which ids exist. |
| A-15 | In Mock mode the customer's access info shows no Drive URL; the «آدرس درایو» row reads «در حالت آزمایشی آدرس واقعی وجود ندارد». Real mode points to the Nextcloud welcome email / configured instance. | A fake URL would imply a real account exists (spec §7: Mock must never look like a real activation). |
| A-16 | Team workspace (bonus §12): one Nextcloud group `abrit-team-{number}` per Team order (`ABR-1405-000124` → `abrit-team-1405-000124`); the ordering customer's account (`abrit-ord1405-000124`) is seat 1; members get `abrit-ord1405-000124-m{n}` (n ≥ 2, never reused) with the plan's per-user quota (500 MB). Seat cap = plan `MaxUsers` frozen at order time (3, owner included). The customer manages members only on their own `Active` Team order; e-mails are trimmed + lower-cased and unique per workspace (owner's e-mail included); a member whose create failed keeps no seat and re-adding the same e-mail reuses its id. | Spec names the feature but not its rules; non-reused ids mean a disabled ex-member's account (and files) can never be handed to the next person. |
| A-17 | Removing a member = remove from the group + **disable** the account (not delete); the seat is freed immediately. If the connector fails, the member stays Active and keeps the seat, and the customer sees a generic error. | Deleting would destroy the member's files irreversibly; the UI must never claim a removal that did not happen (§7). |
| A-18 | Real mode was verified only against a local Nextcloud we ran ourselves (compose profile `nextcloud`) — **not an AbrIT environment**. Mock stays the default everywhere (demo, CI, video). | Spec §9: without an AbrIT-provided instance the official mode is Mock. |
| A-19 | "Reading status from the API" (bonus §12) = admin button «به‌روزرسانی وضعیت از Nextcloud» in the order's provisioning details (permission `ApproveTestPayments`). It reads the order's (owner) account via `GetUserAsync` (enabled, quota, used bytes, groups), stores `LastCheckedUtc` + `LastStatusSnapshot` on the `ProvisioningRequest`, and never changes the order status. A read failure is stored as a sanitized code (`GetUserAsync` now throws `NextcloudConnectorException` instead of returning `null`, so "not found" and "unreachable" stay distinct). Mock answers from its in-memory state (used bytes always 0; empty after a restart → "not found"). | Admin-triggered keeps the external API out of customer page loads; a snapshot is honest about when it was read. |

## Technical decisions

| ID | Decision | Why |
|---|---|---|
| D-01 | Orchard Core 3.0.1 on .NET 10, SQLite. | Latest stable; SQLite allowed for demo (§4.1). |
| D-02 | Service & Plan = Orchard content types, seeded by recipe. | Admin-manageable without code; uses built-in features (§4.1, §7). |
| D-03 | Order & ProvisioningRequest = YesSql documents + map indexes in our module, not content items. | Strict state machine, ownership, idempotency; must not be editable via the generic content editor. |
| D-04 | Orchard Commerce not used. | Optional in spec; its cart/checkout/payment model is heavier than this single-plan flow and would hide the logic being evaluated. |
| D-05 | Pure `Domain` project without Orchard references. | Fast, deterministic required tests; clear module boundary. |
| D-06 | Per-order lock through Orchard `IDistributedLock` + single ProvisioningRequest + deterministic external id. | Three-layer idempotency (see ARCHITECTURE.md). |
| D-07 | Server-rendered Razor + Bootstrap 5 RTL, no SPA. | One deployable; uses Orchard theming; spec asks not to rebuild built-in systems. |
| D-08 | Admin user via Orchard AutoSetup from env vars; demo customers via `DemoUsers` recipe step. | No repeated manual entry (§3) and no secrets in git (§7). |
| D-09 | Seeded catalog uses fixed ContentItemIds (`abrsvc-drive`, `abrsvc-erp360`, `abrsvc-desk`, `abrsvc-itsupport`, `abrplan-drive-starter`, `abrplan-drive-team`), Published + Latest. | The `AbrPlan.Service` ContentPicker must resolve on a fresh setup and later phases/orders reference plans by stable id; re-running the recipe updates instead of duplicating. Extends D-02. |
| D-10 | Recipe feature IDs verified against the 3.0.1 assemblies: `OrchardCore.Users.Registration`, `OrchardCore.Users.ResetPassword`, `OrchardCore.Email.Smtp`, etc. all exist unchanged; Roles step is omitted (Orchard creates default roles; phase 04 permissions reach Administrator via stereotypes). `desk`/`it-support` MoreInfoUrl points to `https://abrit.ir` until exact pages are known. | Avoids guessing feature names; no custom permissions yet. The recipe's `feature` base list is copied verbatim from the built-in Blank recipe (OrchardCore v3.0.1, `src/OrchardCore.Themes/TheAdmin/Recipes/blank.recipe.json`) plus our additions, because dropping base features (e.g. `OrchardCore.Navigation`) broke the TheAdmin theme. Blank sets no front-end theme; we use `TheTheme`. |
| D-11 | Domain owns order numbering (`SequentialOrderNumberGenerator` over `ISequenceStore` + `IOrderLock`) and ids (`IIdSource`); the module only supplies YesSql/Orchard adapters (`YesSqlSequenceStore`, `DistributedOrderLock` over `IDistributedLock`, `OrchardIdSource` over `IIdGenerator`). | Concurrency-sensitive logic is unit-tested in Domain without Orchard (D-05). Trade-off: `YesSqlSequenceStore` increments through the request's scoped `ISession` and calls `SaveChangesAsync` inside the per-year lock, which commits everything pending in that session (numbering runs before the order is saved, so normally only the counter). A second session was rejected because on SQLite it can block on the request's own open transaction. Consequence: if the order save fails after numbering, that number is skipped (a gap) - acceptable, uniqueness is what matters (A-13). |
| D-12 | Order/provisioning persistence inside the per-order lock: (1) `YesSqlOrderRepository.SaveAsync` / `YesSqlProvisioningRequestRepository.SaveAsync` commit (`SaveChangesAsync`) instead of only flushing; (2) `DistributedOrderLock` (scoped) ends the request session's transaction right after acquiring the lock; (3) `Order` and `ProvisioningRequest` carry a YesSql `long Id`; (4) repository reads detach + re-query so they never return a stale tracked instance. | The next lock holder is usually another HTTP request with its own session, so state must be committed before the lock is released and read fresh after it is acquired. Found in the host runtime check: after a commit YesSql no longer tracks earlier-loaded instances, and without an `Id` property the next save of the same object inserted a second document (duplicate orders/requests). Same trade-off as D-11 (a commit includes whatever is pending in the request session). |
| D-13 | Authorization is checked twice: controllers call `IAuthorizationService` with our permissions, and the Domain services (`PaymentApprovalService`, `ProvisioningService.RetryAsync`, `AdminOrderService`) call `IOperatorAuthorizer`, whose Orchard adapter requires the actor to be the signed-in user and to hold `ApproveTestPayments`. The HMAC callback uses a separate entry point (`ApproveFromVerifiedCallbackAsync`, actor `payment-callback`) that shares the same core. | Defence in depth, and AC-08 can be proven by fast unit tests. A separate method keeps "trusted system actor" out of the user-id space. |
| D-14 | Approving an order that is already paid but `Failed` is a no-op (returns the current state); only the admin Retry re-enters provisioning. A Real-mode configuration without the phase-B OCS client registers a placeholder that throws, so orders end `Failed` with `connector_exception` rather than pretending to activate. | Keeps callbacks/double clicks idempotent after a failure and keeps Retry the only "controlled" path (A-02). |
| D-15 | `/` is mapped by the recipe `settings` step (`HomeRoute` → `Services/Index`), Orchard's built-in home-route mechanism, not by a custom route. Mock payment callback: body ≤ 4 KB, JSON `{"orderId": "..."}`, `X-Signature` lowercase or uppercase hex HMAC-SHA256 of the raw body, constant-time compare; 404 when `MockPayment__WebhookSecret` is empty, 401 bad signature, 409 cancelled order. | Uses Orchard's feature instead of competing with its dynamic home route. Callback contract is explicit so it can be scripted (AC-05). |
| D-16 | Real connector = OCS Provisioning API **v1** (`/ocs/v1.php/cloud/...`, `format=json`, `OCS-APIRequest: true`, Basic auth admin + app password) via a typed `HttpClient`. Outcome is read from `meta.statuscode` (100 ok, 102 already exists = success, 404/998 on read = missing, 108 on create without e-mail → retry once with a random password that is discarded). Errors map to fixed codes `NC_AUTH`, `NC_HTTP_{status}`, `NC_OCS_{code}`, `NC_TIMEOUT`, `NC_NETWORK`, `NC_BAD_RESPONSE` with fixed messages — server text, URLs and exception messages are never stored or logged. Replaces the D-14 placeholder. | v1 is what AGENTS.md §6 specifies and reports errors inside a 200 response; fixed messages are the simplest way to guarantee no secret leaks. |
| D-17 | `Microsoft.Extensions.Http.Resilience` (10.6.0 — the same version OrchardCore 3.0.1 already depends on, e.g. `OrchardCore.ReCaptcha.Core`, so no new dependency enters the app) for the OCS client: per-attempt timeout = `Nextcloud:TimeoutSeconds`, **one** transient retry (5xx/408/429/network/timeout, 500 ms + jitter). A retried create is safe because a second `POST users` answers 102. The controlled business retry stays the admin Retry (A-02). | AGENTS.md §6 asks for timeout + max 1 transient retry; hand-rolled retry logic would be less tested. |
| D-18 | `INextcloudProvisioner` gained `AddUserToGroupAsync`, `RemoveUserFromGroupAsync`, `DisableUserAsync`; provisioning now adds the Team owner to the group explicitly (create-with-groups is skipped by Nextcloud when the account already existed). `TeamWorkspace` is a YesSql document (one per order, `TeamWorkspaceIndex(OrderId)`, migration v3) changed only under the per-order lock, with the same commit-on-save / fresh-read rules as D-12. | Same three idempotency layers as provisioning: lock, one document per order, deterministic ids + create-if-missing. |
